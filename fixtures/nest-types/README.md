# nest-types fixture

Exercises the P02 type layer: `TypeCollector`, the registry ids, `structuralHash`,
generics, recursion, the depth cap and the class-validator / class-transformer
field meta. Every construct listed in `roadmap/P02-types.md` §11 ("Fixture") lives
somewhere under `src/`.

The fixture is type-checked, never executed:

```
./node_modules/.bin/tsc -p fixtures/nest-types/tsconfig.json --noEmit
```

`src/validation.ts` is a local stand-in for `class-validator` and
`class-transformer` (no-op factories with the real decorator names) so the
fixture needs no extra install; the reader only looks at decorator names and
their literal arguments.

`types.maxDepth` is pinned to `3` in `flowatlas.config.json`, and
`@fixture/contracts` (`fixtures/shared/contracts`) is the only entry in
`sharedPackages`.

## Pairs that must hash equal

| Pair | Why |
|---|---|
| `Shape1` / `Shape2` (`src/types/shapes.ts`) | Same fields with the same types; they differ only in the type name and in field declaration order. `structuralHash` drops names and sorts fields (D4), so the two hashes MUST be identical — this is the property `contract: shared` in P10 is built on. |
| `type:@fixture/contracts#SharedOrderEvent` collected from this repo vs from any other repo listing `@fixture/contracts` in `sharedPackages` | Same declaration resolved through the same shared package: same id, same hash, so P05's registry merge dedupes it instead of throwing (D7 / §10 "two `node_modules` copies"). |

`Shape1 → Shape2` is also assignable in TS (`CatalogService.shapes`), which keeps
the compiler honest about the two being structurally identical.

## Deliberately unresolvable constructs

| Where | Construct | Expected `unresolved.reason` |
|---|---|---|
| `src/orders/orders.service.ts` — `import { LegacyOrder } from '@acme/legacy-orders'`, used by `fromLegacy()` | The package is not installed, so the import is an error type | `type-unresolved` (hint: "install deps or fix tsconfig paths"). The `TypeRef` is `unknown` and no entry is registered — never a guessed shape (I3). This is also the **only** `tsc` error the fixture is allowed to produce (`TS2307`). |
| `src/types/deep.ts` — `L0.inline: { a: { b: { c: string } } }`, reached via `CatalogService.deep()` / `GET /catalog/deep` | Anonymous nested object below `types.maxDepth: 3` | `type-depth-exceeded` (info, `meta.level: 'info'`; hint: "raise types.maxDepth"). Emitted once per cut site and only for the anonymous shape: the named chain `L0 → L1 → L2 → L3 → L4` is still registered in full, five entries. |
| `src/catalog/catalog.service.ts` — `wrap<T>(items: T[]): Paginated<T>` | Generic used with a type argument that is unknown at the site | `type-generic-uninstantiated` (info). The ref is `type:nest-types#Paginated<T>` and points at the bare `kind: generic` template entry, not at an instantiation (D6). |
| `src/orders/dto/create-order.dto.ts` — `@Transform(({ value }) => String(value).trim())` | The decorator argument is an arrow function, not a literal | `decorator-arg-dynamic` (reused from P01). The field still gets `meta.transform: true`. |

Everything else must resolve. In particular `Logger`
(`OrdersService.logTo`) comes from `@nestjs/common`, which is in `node_modules`
and is *not* a shared package: it is registered as `kind: external` with no
fields (D7), which is a resolved outcome, not an unresolved one.
